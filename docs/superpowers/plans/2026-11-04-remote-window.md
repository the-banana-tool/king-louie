# The Remote Window (Stage 3, Part B) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** From a laptop away from home, the owner opens a tab onto a node behind the front door, reads and continues its chats with a press per acting call on the phone, and a dropped socket costs a reconnect, not a turn; the front door passes sealed bytes it cannot read.

**Architecture:** The window stays one renderer for one node: one `BaseWindow` holds a tab strip and one `WebContentsView` per node, each with its own session partition and its own host in the main process, routed by `event.sender`. A remote tab dials `wss://mcp.<domain>/window/v1` with an OAuth bearer (scope `window:attach`, audience `/window/v1`); the front door asks the node over the existing link to dial back `wss://mesh.<domain>/window/v1/<session>` with its pinned client certificate, and splices the two sockets byte for byte. Inside the splice the window and the node run a one-round-trip authenticated X25519 exchange signed by the window's `kld-` Ed25519 key and the node's identity key over a transcript that includes the session id, then exchange padded ChaCha20-Poly1305 records that carry the existing bridge frames. On the node the `DesktopBridgeServer` takes many connections at once, a sealed one through an in-process stream (no second listener), and the dispatcher marks a remote device's events `remote-window`, never local: every channel and call method has a class in one table, phone-class calls become signed phone approvals over the exact arguments, and a remote drop stops nothing. Enrollment is a sealed `kl.window.enroll` the phone answers only after its Scanner reads a QR of the full SHA-256 over the device key and the node key.

**Tech Stack:** `node:crypto` only (X25519 via `generateKeyPairSync('x25519')`/`diffieHellman`, `hkdfSync`, `createCipheriv('chacha20-poly1305')`, Ed25519 as today); `ws` and `tls` as the mesh link uses them; Electron 41.0.4 (`BaseWindow`, `WebContentsView`, `session.fromPartition`, `ses.protocol.handle`); `qrcode` (already a dependency) for the enrollment QR; node's built-in test runner; vectors in `tests/vectors/window-v1/` and `tests/vectors/approval-v1/`.

**Spec:** `docs/superpowers/specs/2026-11-04-attach-stage3-design.md` §4 to §13 (binding: §2 decisions 1 to 5 and 8, §3). Part A is built (`docs/superpowers/plans/2026-11-04-sealed-phones.md`, R-SP-1 to R-SP-15): every new node-to-phone content type is born sealed through `SEAL_TABLE` (R-SP-14). Part C (§15) is a later plan; this plan names only the seam it needs (R-RW-21).

The front door's splice lives under `src/frontdoor/window/` and the window message types under `src/approvals/`, so the front door, relay and runbook graphs load nothing from `src/desktop-bridge/` (`tests/service-profile-graph.test.js` gains `src/desktop-bridge/` in `FORBIDDEN`, Task 7).

- A change to approval-v1 is complete only after `node tests/vectors/approval-v1/generate.js` and `--check` pass (69 today) and the names are in `tests/approvals-protocol.test.js`; the same for `tests/vectors/window-v1/generate.js`.

## Review Focus

1. A second window sends into a chat whose turn is running (two tabs on two machines onto one node): the second `chat:sendMessage` must be refused `CHAT_BUSY`, not start a second run. The spec says the "existing busy refusal" does this; there is none (`activeRuns` in `src/ipc/chat-handlers.js:494-499` is a Set per chat, and only a task's chat refuses). Test in Task 2.
2. A window reconnects while a run it started is waiting on `agent:askUser`: the prompt must be shown again on the new connection and its answer accepted, and a prompt whose window never returns must still time out (5 minutes) rather than hold the turn. Test in Task 3.
3. A phone-class call whose arguments pass 256 KiB (`case:ingestFiles` with a PDF): the approval carries the hash and the summary, the node runs the bytes it hashed, and a second call with the same hash but different bytes is refused. Test in Task 3.
4. The front door attaches the wrong node (its registry entry swapped after the window pinned): the window's pin check on the node's signature fails before any bridge frame, the tab says `SERVICE_KEY_CHANGED` and nothing is sent. Test in Task 4 (the seal) and Task 16 (hostile front door).
5. A remote device whose record is revoked on the phone while its session is live: the node's 5 s re-read closes the session, and a frame already in flight after the revoke is answered with nothing. Test in Task 5.

## Rulings (what the spec left open, decided here)

Each is the author's call; the owner may overrule. The plan builds on them as written.

- **R-RW-1, one window-v1 protocol, written before the code.** `docs/protocol/window-v1.md`, with vectors, as approval-v1 has. Version byte `0x01`. Frames are binary WebSocket messages on both legs of the splice. Handshake, one round trip, identities in clear so the audit can name the device (R-RW-4): W→N `hello_w = 0x01 ‖ 0x01 (version) ‖ eW (32) ‖ device_id (20 ASCII) ‖ pub_dev (32 raw Ed25519)`; N→W `hello_n = 0x02 ‖ eN (32) ‖ node_id (19 ASCII) ‖ pub_node (32) ‖ sig_node`, where `sig_node = Ed25519(node_sk, "kl-window-v1\nnode\n" ‖ session_id ‖ hello_w ‖ hello_n[0..83])`; W→N `auth_w = 0x03 ‖ sig_dev = Ed25519(dev_sk, "kl-window-v1\nwindow\n" ‖ session_id ‖ hello_w ‖ hello_n)`. Keys: `ss = X25519(eW, eN)`; `prk = HKDF-Extract(SHA-256, salt = SHA-256(session_id ‖ hello_w ‖ hello_n), ss)`; `k_w2n = HKDF-Expand(prk, "kl-window-v1 w2n", 32)`, `k_n2w = … "n2w"`. The window verifies `sig_node` against its pin (or, on first attach, against the key the front door gave, which the QR enrollment then binds) before `auth_w` leaves; the node verifies `sig_dev` against `desktop-devices.json` before it sends anything but a close. A signature that fails, a `session_id` that differs on the two sides, or a wrong first byte closes with `4401`. Forward secrecy holds from the ephemeral keys; no rekey in v1 (a session is reconnected instead; counters are 64-bit).
- **R-RW-2, records.** `record = 0x10 ‖ counter (8, big-endian, from 0, per direction) ‖ ct`, `ct = ChaCha20-Poly1305(key_dir, nonce = 0x00000000 ‖ counter, plaintext, aad = 0x01 ‖ dir (0x00 w2n, 0x01 n2w) ‖ counter)`. Plaintext is `kind (1) ‖ len (4) ‖ bytes ‖ pad`, `kind` one of `0x00` final fragment of a bridge frame, `0x01` more fragments follow, `0x20` ping, `0x21` pong, `0x30` close (bytes = a 4-byte code). A bridge frame over `RECORD_MAX = 1048576` bytes goes as fragments; a frame over `LIMITS.frameBytes` (64 MiB) is refused by the receiver with `PAYLOAD_TOO_LARGE` as today. **Padding (learned from part A):** `pad` brings `len(plaintext)` to a multiple of 256 bytes when the frame is under 65536 bytes, else of 4096; so a short chat delta, a `chat:stopResponse` and a `result` with `ok: false` are not told apart by length, at a cost of at most 255 bytes a record (the mesh link pads nothing; the splice sees sizes and timing anyway, which the docs say). A counter that is not the expected one, a tag that fails, a `kind` the table lacks or a fragment run over 64 MiB closes the session `4400` and no later record is read. Ping every 20 s from both sides; 60 s without any record closes `1001` and the window reconnects.
- **R-RW-3, the splice.** The window opens `GET /window/v1?node=<node_id>` on `mcp.<domain>` with `Authorization: Bearer kla_…` and `Sec-WebSocket-Protocol: kl-window-v1`. The front door checks, in order: the token (`tokens.authenticate(token, { aud: windowResourceUrl })`, `windowResourceUrl = <origin>/window/v1`), the scope (`allows(scopes, 'attach_window', { required: 'window:attach', machine: node_name })` plus `grants.machineMatches`), the node (registered and online, else `4404 node_offline` before anything is asked), the limits (R-RW-5). It mints `session_id` (32 random bytes, base64url), answers `101` with header `x-kl-window-session: <session_id>`, and calls `nodeHub.rpc(node_id, 'window.open', { session_id, expires_at })` (10 s). The node answers `{ ok: true }` or a refusal (`remote_window_off`, `too_many_windows`), which closes the window's socket with `4403` and the refusal's code. The node dials `wss://mesh.<domain>/window/v1/<session_id>` with its TLS client certificate and the front door's pinned certificate (as `connectPinned` does; `src/desktop-bridge/window-dialer.js` reuses `MeshTransport`'s pin check and nothing of its handshake). The mesh listener already refuses a client certificate that is not a pinned node's at the TLS layer (`src/frontdoor/tls/sni-listener.js:267-288`); the splice maps the presented fingerprint to one registry record and requires `record.node_id === session.node_id`, else `socket.destroy()`. A session not dialled within 30 s is closed `4408`. **Nothing more signs the dial-back:** the client certificate is the node's identity at the TLS layer on a socket the front door itself terminated, so an exporter-bound frame would prove what the handshake already proved; the seal (R-RW-1) then binds the two ends to each other and to `session_id`, so a front door that spliced the wrong node fails the window's pin check. Could a node splice into another's session? No: a session is dialled once (the first upgrade wins, a second is destroyed), its id is 256 random bits never sent to a client, and the dialling certificate must belong to the node the session names. Could a client? No: the client leg is created by the bearer's holder and the id is only ever sent to that socket's 101 response.
- **R-RW-4, what the front door keeps.** `WindowSessions` (`src/frontdoor/window/sessions.js`) holds per session `{ session_id, grant_id, client_id, node_id, device_id (from the clear `hello_w`, read by watching the first window frame only; null when the handshake never completes), opened_at, bytes_in, bytes_out }`. Audit (own ledger): `window.session.opened { session_id, grant_id, client_id, node_id }`, `window.session.closed { session_id, device_id, bytes_in, bytes_out, seconds, reason }`, `window.session.refused { grant_id, client_id, node_id, code }`. No frame content is ever parsed past the handshake's first byte and fixed offsets; a `hello_w` that is not 86 bytes is passed through unread and `device_id` stays null. `onGrantRevoked(grant_id)` closes that grant's sessions `4403 grant_revoked`; an access token expiring does not close a session (R-RW-10). `docs/fleet/front-door.md` gets a section "What the front door sees of a window" (ids, sizes, timing; never text), the neighbour of `mobile/PRIVACY.md`.
- **R-RW-5, limits.** `frontdoor.window: { max_sessions_per_grant: 4, max_sessions_per_device_node: 2, max_bytes_per_hour: 1073741824, idle_s: 600 }` (`FRONTDOOR_KEYS.top` gains `window`; strict keys; the byte budget is per session per rolling hour in both directions together, past it the session closes `4429 byte_budget` and the tab says so and retries after 60 s). `max_sessions_per_device_node` is counted by `device_id` once known. The 20 s ping keeps a live session under `idle_s`.
- **R-RW-6, the bridge server takes many connections.** `DesktopBridgeServer.live` becomes `connections: Map<id, conn>`; `connected` answers the list; `4409 OTHER_DEVICE` goes, replaced by `4409 TOO_MANY_WINDOWS` at `LIMITS.maxDevices = 8` connections (local and remote together, spec §9). The same device id attaching again replaces its own earlier connection (one connection per device per node). `_recheckLive` walks every connection. `conn` gains `remote: boolean`, `label`, `deviceId` as today; `createConnection({ remote })`. The dispatcher's `getConnection()` goes: the run's connection is read from an `AsyncLocalStorage` the dispatcher enters around every `handlers.get(channel)(makeEvent(conn), …args)` (`src/desktop-bridge/run-context.js`, `runFor(conn, fn)`, `currentConnection()`), so `prompter.askUser` and `requestDirectoryAccess` reach the connection whose invoke started the run, which the awaited `chat:sendMessage` keeps alive for the whole turn. A prompt with no current connection (a wake-up, cron) goes to the oldest live local connection, else answers as the headless prompter does.
- **R-RW-7, who gets which event.** `pushEvent(conn, channel, payload)` sends `PROMPT_EVENTS` and `canvas:executeJs` to the run's connection only, and `tool:approvalRequired` only when that connection is local; every other renderer event (`chat:messageStart/Chunk/Complete/Error`, `chat:toolUse/toolResult/toolProgress`, `chat:updated`, `case:changed`, `models:*`, workflow events) goes to every live connection, as `forwardAmbient` does, so two windows show the same chat. A remote run's `askUser` goes to its own connection (typed words are the owner's, spec §8; it is a question, not a gate); its `requestDirectoryAccess` becomes a phone approval of the pseudo-tool `AllowDirectory` with `{ directory, toolName }` through `approvals.phoneApprover.requestApproval` (R-RW-12's shape), refused `false` with no phone.
- **R-RW-8, a remote drop stops nothing.** `onDisconnect(conn)` for `conn.remote`: no `chat:stopResponse`, no "The desktop disconnected" row, no denials (a remote connection is never shown an approval or a directory prompt); the import it had open is still aborted (a half-sent chat is useless); `conn.prompts.askUser` entries move to `pendingAskUserByDevice.get(deviceId)` with their chat id and payload, and the next connection of that device is sent each `agent:askUser` again (the resolver and its 5-minute timer are untouched, so an answer from the new connection lands and a window that never returns times out as today). A local connection keeps stage 2's behaviour. Reconnect: the renderer calls `chat:load` as it does on start, and the new read channel `chat:running` (`→ { ok, chatIds: string[] }` from `context.isChatRunning` over the chats loaded) tells it which chats have a turn under way, which it shows as running with Send disabled until `chat:messageComplete`, `chat:messageError` or `chat:updated` for that chat arrives.
- **R-RW-9, the remote origin.** `src/core/origin.js` gains `markRemoteWindowEvent(event, { deviceId, approved = null })`, `isRemoteWindowEvent(event)`, `remoteWindowDeviceId(event)`, `remoteWindowApproved(event)` (the phone's `request_id` when the dispatcher's phone gate approved this call, else null), with a `WeakMap` as the local marks have. The dispatcher calls `markRemoteWindowEvent` for `conn.remote` and `markLocalDesktopEvent` otherwise; `tests/core-origin.test.js` pins the caller list of both. `approvalSeam` reads the mark (the audit of Task 1): a remote run, or a child carrying its origin, has `denyAutoApproval` in every mode, a requester that answers `false` at once in `allow` and `deny`, and a `classifyCall` under which every tool a task's turn removes for outliving it, plus `SpawnAgent` (`outlivesRemoteTurn`, `src/approvals/outliving-tools.js`, the list `src/tasks/values.js` reads), is `unsafe`, so it goes to the phone. The turn's typed words are the owner's (spec §8): the seam sets `remoteWindowTurn` on the event's own run alone, so a `requiresOwnerTurn` tool and its quote check get `ownerTurnText` while `denyAutoApproval` keeps `ownerQuote`, always-approve, `allow` and `autoApproveTools` shut; the case tools run on the channel `remote-window`, checked as `in-app-chat` is, which is no press, reviews no document and never confirms an objective. `runOrigin` gains `{ client: 'remote-window', deviceId, session, job_id: null }` for a remote event, which is what the phone's origin shows and the audit's `auditOriginOf` reduces to its kind. `remote-window` joins no press list (`APP_ANSWER_CHANNELS`, `PRESS_CHANNELS` are untouched; a test asserts the word is in neither).
- **R-RW-10, OAuth.** The window is a public PKCE client registered once per front door through `POST /oauth/register` (`client_name` `King Louie window`, `redirect_uris: ['http://127.0.0.1/kl/window/callback']`); `redirectAllowed` accepts a loopback `http:` URI whose scheme, host and path equal a registered loopback URI with any port (RFC 8252 §7.3; `https:` stays exact). The scope `window:attach` is registered by `src/frontdoor/window/scope.js` through `TOOL_EXTENSIONS` (`tools: ['attach_window']`, description `Attach a King Louie window to a machine`), advertised only when listed in `scopes_enabled`, and takes `;machines=`. The second resource is `windowResourceUrl`; `authorize` accepts `resource` equal to either; `/.well-known/oauth-protected-resource/window/v1` describes it; the token's `aud` is whichever was asked, so an MCP token opens no window socket and a window token calls no MCP. The consent is the phone-signed `kl.client.grant` unchanged (`resource` is already in it). The window stores `{ clientId, accessSealed, refreshSealed, expiresAt }` under its node entry with `state.seal`. Access tokens last 1 h: the window refreshes before each connect when under 5 minutes remain and on a `401` at upgrade; a live session is bound to the grant, not the token (R-RW-4). The authorization code is received by a loopback `http.createServer` on `127.0.0.1:0` opened for that flow only, closed after one request or 10 minutes; the browser is opened with `shell.openExternal` from the controller (Electron side).
- **R-RW-11, the class table.** `src/desktop-bridge/remote-classes.js` exports `REMOTE_CLASSES: { [channelOrMethod]: 'read' | 'ordinary' | 'phone' | 'local' }`, `remoteClassOf(name)`, `remotePayloadClass(channel, args, context)` and `assertComplete(names)`; its content is the appendix of this plan, built from `listIpcChannels()` under personal hosting plus the nine `t:'call'` methods. The dispatcher asks `remotePayloadClass`, which only raises the table's class and answers `phone` for what it cannot read: `case:create` with `playbooks` or `acceptBudgetRaises` present; `models:removeProfile`, `models:setDefaultProfile` and `models:setChatProfile` when they leave a profile with `localOnly` (read from `getSettings`/`getChat`; a case chat, whose choice is in `case.yaml`, is always `phone`). Three `read` or `ordinary` channels hold the rest in their handlers, on a remote event: `settings:mcpList` shows each `env` value and argument as its `${vault:…}` reference or `(hidden)`, `settings:load` drops `webSearch.*.apiKey` and `imageGeneration.*.apiKey`, and `chat:addMessage` adds only a `user` or `assistant` row with no other field (`REMOTE_MESSAGE_REFUSED`). `checkpoint:list` and `checkpoint:changes` read only an allowed directory, a chat's working directory or the host's (`REMOTE_PATH_REFUSED`), and `changes` and `restore` take only a 40-hex id, one of that directory's for `changes` (`CHECKPOINT_NOT_HERE`). `local` means the node never serves it to a remote connection: the dispatcher answers `{ ok: false, code: 'REMOTE_LOCAL_ONLY' | 'REMOTE_PRESS', error }` (`REMOTE_PRESS` for the pressed questions and owner presses, whose card then says `Answer on your phone`). `tests/desktop-bridge-remote-classes.test.js` fails when any channel `servedChannels` serves under either hosting, any `desktop:`/`wizard:`/`LOCAL_CHANNELS` name, or any `callMethod` case lacks a class, or when a `phone`-class channel is one the stage 2 recon lists as running code, writing files or returning secrets but the table says `read` or `ordinary`. The sweep (Task 16) drives each class through the dispatcher from a remote connection.
- **R-RW-12, the phone gate for a channel call.** For a `phone`-class channel or method the dispatcher, before the handler, calls `approvals.phoneApprover.requestApproval('Window', params, { origin })` with `params = { channel, args }` when `JCS(args)` is at most `WINDOW_ARGS_INLINE_MAX = 65536` bytes, else `{ channel, args_sha256: b64url(SHA-256(JCS(args))), bytes }`; the approver's action is kind `tool`, name `Window`, `summary` `${channel} from ${label}` (one plain line, 120 characters, through `plainLineProblem`), `cwd: null`, so both phone cores show it with no change. The node keeps the args in memory keyed by the approval's `request_id` for the approval's TTL (`TTL_MAX_MS`, 5 min) and runs exactly the object it hashed; a second call presenting the same hash with different bytes is a new approval. No `phoneApprover` (standalone, a node without approvals) refuses `NO_PHONE`. `tool:execute` is gated here like every other `phone` channel; its handler then builds a `ToolExecutor` whose event is remote, so the tool it runs also asks through `approvalSeam` when the tool gates: the first approval is of the channel call, the second of the tool. A `Bash` card on a remote turn with the chat's sandbox off starts `Sandbox off: `, ahead of any cut, and `chat:sendMessage` ignores the payload's `sandboxMode` for a remote event and reads the chat's stored value. A `phone` call that the owner denies is answered `{ ok: false, code: 'PHONE_DENIED' }` and audited as any denial. Each approved call marks its event `approved: request_id` (R-RW-9) so a handler that needs to know (R-RW-13) can.
- **R-RW-13, the gates the spec names.** Private marks (`chat:markPrivate`, `case:markPrivate`) are `phone` class, and `private-mark.js`'s `precheck` accepts `isLocalDesktopEvent(event) || remoteWindowApproved(event) !== null`; a remote call without the gate's approval (there is none: the dispatcher always gates) stays `NOT_LOCAL_WINDOW`. `NOT_LOCAL_DESKTOP` gates (`case:confirmScope`, `case:verifyNow`, `case:setCheck`) stay closed: `local` class, `REMOTE_PRESS`. `case:create`'s objective from a remote window is recorded as proposed (`case-handlers.js:148` already does this for an unmarked event; the warning line is kept) and the `scope-confirm` question is answered on the phone. Presence: `contact-handlers.js`'s heartbeat answers a remote event `{ ok: true, counted: false }` and tells presence nothing, so it counts neither toward `presentChannel` nor as the owner at a window, and questions keep going to the phone (the audit of Task 1, which reverses spec §10: a focused tab does not show who holds the laptop). `models:local.*` keep their null-device-id rule (`NOT_LOCAL_WINDOW`) and are `local` class. `skill:install`'s relative-path rule reads `localDesktopDeviceId(event)` or `isRemoteWindowEvent(event)`, so a relative path is refused `RELATIVE_PATH`; the handler is `phone` class, so an absolute path names the node's disk, which the approval shows.
- **R-RW-14, enrollment messages (born sealed, R-SP-14).** `kl.window.enroll` (node-signed, the mailbox type `kl.window.`, TTL 10 min, `message.submit` with push `{ kind: 'window', id: request_id }`; `KINDS` gains `window`, fcm only like the session kinds): clear `v, type, request_id, node_id, node_name, enroll_hash, created_at, expires_at, nonce, node_box`; content `window: { device_id, public_key (b64url raw Ed25519), label, platform: 'windows' }, node_key (hex SPKI of the node's Ed25519 key, the window's view of it), salt`; `enroll_hash = saltedHash(salt, { window, node_key })`. The QR the window shows is `kl1:` + base64url of JCS `{ t: 'kl.window', h: b64url(SHA-256(raw_device_key (32) ‖ raw_node_key (32))) }`; the phone computes `h` from the opened `window.public_key` and **its own pinned key for `node_id`** (never from `node_key`, which is shown only so the owner can see it matches) and enables Allow only on equality. The answer is `kl.window.enroll.response` (device-signed, device key only; `read` key refused `bad_signature`): `v, type, request_id, node_id, enroll_hash, nonce, decision ('approve' | 'deny'), device_id, expires_at, signed_at`, posted to `POST /v1/windows/enroll` (auth `device`), forwarded as node method `window.enroll_response`. `kl.window.revoke` (device-signed): clear `v, type, node_id, window_id, device_id, created_at, expires_at, nonce`, content `reason`; `POST /v1/windows/revoke` (auth `device`) → node method `window.revoke`. `kl.window.list` (node-signed, to one device): clear `v, type, node_id, to_device, at, nonce, node_box`; content `windows: [{ device_id, label, platform, enrolled_at, attached: boolean }]`; `GET /v1/windows` (auth `read`) fans `window.list` out to every node the device is active on and returns `[{ node_id, envelope | null }]`. All four join `SEAL_TABLE`, `tests/sealed-types.test.js`'s `CONTENT_TYPES`, and approval-v1's vectors.
- **R-RW-15, where a window's record lives.** `desktop-devices.json` records gain `remote: true` (`parseDevices` accepts the optional boolean, `upsertDevice` writes it, `findDevice` returns it); a record's `remote` decides its path: a local pairing's key is refused on the splice (`4403 not_remote`) and a remote device's on the loopback listener (`4403 UNKNOWN_DEVICE`). On a personal node the service owns the config dir and `WindowEnrollment` writes the record itself on an approve. On a fleet node the service cannot: the approved pair (the node's request envelope and the phone's response envelope) is staged under `<dataDir>/approvals/staged/` as type `kl.window.enroll.response` and `king-louie-service device apply` verifies both (the response by an active approver's device key, the request by this node's own key, the decision `approve`, the hash equal) and writes the record (`window <label> (kld-…) enrolled`, audited `window.enrolled`); a revoke is applied the same way (`window revoked`, audited `window.revoked`) after the node has already closed the sessions from its in-memory overlay. A revoke on a personal node removes the record at once. `windowEnrollment.isEnrolled(deviceId)` reads the file plus the overlay on every ask, so the 5 s re-read closes a revoked session.
- **R-RW-16, the window's state.** `desktop-state.js` adds `nodes: []` and keeps `pairing` as a view of the entry with `kind: 'local'`. An entry is `{ id (uuid), kind: 'local' | 'remote', deviceId, publicKey, privateKeySealed, label, service: { nodeId, publicKey, name, port?, hosting?, dataDir? }, frontDoor: null | { origin, clientId, accessSealed, refreshSealed, expiresAt }, enrolled: boolean, order, open: boolean }`. On open, a store with `pairing` set and `nodes` empty gets `nodes = [{ ...pairing, id, kind: 'local', frontDoor: null, enrolled: true, order: 0, open: true }]` and `pairing` is thereafter read from and written through that entry (`setPairing`, `clearPairing` act on it), so stage 2's controller is unchanged. `pendingPair`, `setup`, `migration` stay singular (they are the local node's). A remote entry's device key is generated per node at Add; revoking one on a node tells nothing of another.

### What the spec does not cover, or gets wrong

- §9: "Two windows sending into one chat: the second gets the existing busy refusal." There is no such refusal: `activeRuns` is a Set of runs per chat and only a task's chat answers `CHAT_BUSY` (`chat-handlers.js:133-136, 494-499`); the renderer disables its own Send box, which a second window does not see. Task 2 adds the refusal for a bridge send into a running chat.
- §4: "the app's custom schemes (`kl-screenshot:` and the rest)". `main.js` registers one scheme, `kl-screenshot`. Per-session registration is of its handler alone.
- §7 step 4 says the node records the device "in `desktop-devices.json`"; on a fleet node that file is administrator-owned (`assertAdminOwned`, `bridge-server.js:435`) and the service cannot write it. R-RW-15 stages and `device apply` writes, as the spec's "my call" allows.
- §8's table lists `tool:execute` under phone with the other channels. It gets the dispatcher's gate like them; the tool it runs asks too (R-RW-12).
- §10 counts a focused remote tab as the owner at a window. The audit of Task 1 reverses that: a remote heartbeat is accepted and counts for nothing (R-RW-13).
- §8: "Local-only gates stay closed: … `NOT_LOCAL_DESKTOP`, and private marks, which become phone approvals rather than refusals." Read two ways; R-RW-13 keeps `NOT_LOCAL_DESKTOP` closed and turns private marks into phone approvals.
- §6 asks for a session id "which binds the session and refuses a splice into another one" and §5 says the node dials "with its pinned TLS identity"; the spec does not say what else the dial-back carries. R-RW-3 carries nothing more and says why.
- §10: "A new read channel fetches the bytes from under the node's own screenshot dir". `main.js:78-90` serves the *window's* `os.tmpdir()`; so does the current `kl-screenshot:` handler. Both move to the node (R-RW-19).
- §12's hostile-front-door test "swaps the device key or the node key during enrollment": the device key reaches the phone inside the node-signed, sealed `kl.window.enroll`, so the front door cannot swap it; it can only swap what the window shows (the QR) or the node key it hands the window. The test swaps those (Task 16).
- Part A's plan counted 68 approval-v1 vectors; the branch has 69. This plan counts from 69.
- The recon (§2) says personal adds 51 channels; the branch registers 263 handle channels and serves 204 of them under personal and 153 under the fleet, with 3 `on` channels and 9 call methods (the appendix is from the code, not the recon).

- **R-RW-34 (controller, after Task 4's review).** A window trusts a node key only after a code from the phone. Without this, a window on first attach goes ready against any key the front door hands it, and that key can answer `window.enroll` and `window.enrollStatus` itself: nothing the phone decides reaches the window authenticated. So the QR gains `n`, 16 random bytes made after the handshake and never sent on any socket: `{ t: 'kl.window', h, n }`. `h` is unchanged. After Allow on a matching hash, the phone shows a 6-digit code, the decimal reduction of the first 8 bytes of SHA-256(`kl-window-confirm-v1\n` ‖ n ‖ raw_device_key ‖ raw_node_key (its own pin)). - **R-RW-35 (controller, after Task 4's review).** The seal owns one ordered writer, `write(bytes)` at construction: every record reaches it in the tick it was sealed. - **R-RW-36 (controller, after Task 4's review), Task 9's enroll-only seam.** Not a lookup that answers the claimed key, which gives the same `peer` as an enrolled device.
